cairn core/ — 追記専用ストレージ層

cairn / 98f23d6  ·  対象: src/cairn/core/（9ファイル・約1,300行） ·  リンクは VS Code で開きます

src/cairn/core/ は、cairn が「プラットフォームとして固定する部分」— オブジェクトストレージ上の追記専用台帳そのものです。DB もロックサービスも使わず、S3 / GCS / ローカルの file:// を fsspec 経由で同じコードから叩きます。

データセットは rows/{ulid}.json への追記ログで、現在の状態はそれを ULID 順に適用した結果（upsert と tombstone、last write wins）。評価は「run を作る＝データセットのスナップショットを固定する」→「予測が別プロセスから書き戻される」→「採点して result/row.json を書く」の三段で、その row.json が在るかどうかだけが「評価済みか」を決めます。

読み出しは二経路。行ファイルが parquet チェックポイントに全部覆われているときだけ DuckDB で直接ページングし、1件でも覆われていない行ファイルがあれば Python で全ログを畳みます。

この層の判断はほぼすべて「S3 にはロックが無い」という一点から派生していて、その代償はロックではなく ゴミ集め（vacuum）と全ログ再生のコスト に付け替えられています。

この一覧の確度について

この範囲には履歴がありません。 リポジトリのコミットは 98f23d6 一つだけ（スカッシュ済み）で、fix / revert / perf のコミットも、バグ修正の差分も存在しません。会話ログも渡されていません。

ただしこのコードベースは珍しく、理由が docstring とコメントに直接書かれています。テスト名も「何を拒むか」を文章で述べる形式です。そのため下のカードの多くは コード確認済み になっていますが、それは「コード中に理由が書いてある」という意味であって、「その理由が当時の実際の動機だった」ことの証明ではありません。

コード確認済み

並行性

選んだ方式書き込みは必ず新しいキーを作る（rows/{ulid}.json、ingests/{ingest_id}.json、manifest/{ulid}.parquet）。削除も上書きではなく墓標 {"op":"delete"} の追記。既存キーへの上書きは、run の _meta.json 更新・予測ファイル・vacuum の3つしか無い。
理由モジュール docstring と README「Lock-free」節に明記。CAS もリースも DynamoDB も要らなくするため。S3 が保証するのは PUT の原子性だけで compare-and-swap は持たないので、「上書きしない」を守れば排他が要らなくなる、という取引。
代償（すでに払っているもの）現在の状態を知るのに必ず全ログの再生が要る（merge）。真実が一箇所になく、rows/ を全部読むまで「今何行あるか」すら分からない。そのために checkpoint と snapshot という派生物が必要になり、そのぶんキー数と GC の面倒が増える。
壊れ方（条件が揃えば起きること）追記が増えるほど merge の時間とメモリが、行数ではなく 追記回数 × その回の ops 数 に比例して伸びる。最初に出る症状は、一覧より先に cairn eval create-run が遅くなること — create_run が snapshot を呼び、それが全マージを含むため。（構造からの推論。実測値ではない）

並行性

選んだ方式同一ミリ秒内では tail を引き直さず +1。時計が巻き戻ったら _LAST_MS を据え置いてやはり +1。新しいミリ秒に入った時だけ os.urandom(10) >> 1 で引き直す（最上位ビットを落として、桁上がりがタイムスタンプ部に食い込まないようにしてある）。排他はプロセス内の threading.Lock。
理由docstring に明記。「rows は ULID 順にマージされるので、キー順＝書き込み順でなければ last write wins が意味を持たない」。乱数のままだと 連続4回のうち2回が逆順になった、と docstring が具体的に書いている。
代償（すでに払っているもの）順序が保証されるのは1プロセス内だけ。_LOCK はプロセスローカルなので、web を複数ワーカーで動かす／複数ジョブが同じデータセットに書く、といった構成では順序は決まらない（docstring も「それらは元々順序づけられていない」と割り切っている）。
壊れ方（条件が揃えば起きること）「同じ行への upsert と delete が、別プロセスから同一ミリ秒に出る」と順序が不定になり、削除したはずの行が残る（またはその逆）。最初に出る症状は、削除が効いたり効かなかったりする非決定性で、単一プロセスのテストでは絶対に再現しない。規模ではなくデプロイ形態（ワーカー数、同時に書くジョブ数）で入る条件。

アルゴリズムとデータ構造

選んだ方式CHECKPOINT_EVERY = 16。追記のたびに「未カバーの行ファイル数 ≥ 16」を判定し、超えたら全行を畳んだ parquet を書く。読み出し（rows_page / count_rows）は未カバーが0件のときだけ DuckDB のページングを使い、1件でも残っていれば Python の全マージに落ちる。
理由定数の docstring に明記。「毎回 checkpoint すると取り込みが二次オーダーになる。間の読み出しは未カバーの行ファイルをマージすることで正しさを保つ」。
代償（すでに払っているもの）checkpoint 直後に1回でも追記が入ると未カバーが1件になるので、実運用のほとんどの時間で読み出しは全マージ経路にいる。「メモリに載せずにページングする」という DuckDB 導入の狙いは、16回に1回訪れる窓の中でしか働いていない。
壊れ方（条件が揃えば起きること）行数が増えると、一覧の1ページ目を出すのに全行をメモリへ載せる。最初に出る症状は、データセット詳細ページの初回表示だけが重くなり、しかも offset を進めても軽くならない（ページ送りが速くならない）こと。加えて追記16回ごとに全データを畳み直す parquet 書き込みが挟まるので、取り込みのレイテンシが周期的に跳ねる。

選んだ方式merge は行ファイルを ULID 順に読み、upsert なら state[key] = row、delete なら pop。それ以外の op には else が無く、何も起きない。
理由テストが理由を書いている（test_an_operation_from_a_newer_writer_is_skipped：「rows は追記専用なので、未知の op は致命傷ではなく無視されるべき」）。新しいバージョンの writer が書いた op を、古い reader が読んでも死なないようにするため。

I/O とネットワーク

選んだ方式write_bytes は file:// のとき {path}.tmp-{ulid} に書いて mv する。リモートはそのまま open→write。write_many はリモートだけ fs.pipe の一括、ローカルは1件ずつ（＝一時ファイル経由を保つ）。makedirs の失敗は握り潰す。
理由コメントに明記。「ローカルの書き込みは原子的でないので、読者が半端なファイルを見うる。オブジェクトストアは PUT を原子的に公開するので一時ファイルは要らない」。makedirs を握り潰すのは「オブジェクトストアにディレクトリが無い」ため（pyproject で ruff の S110 を明示的に無効化してある）。
代償（すでに払っているもの）ローカルでは書き込みが常に2倍のファイル操作になり、一括書き込みの高速化を諦めている。そして .tmp-{ulid} が残る経路がある — mv の前に落ちるとゴミが残り、vacuum は checkpoint しか見ないので誰も消さない。
壊れ方（条件が揃えば起きること）実測して確認した： rows/ に残った tmp ファイルは files() の分類を素通りする（manifest は .json で絞っているが rows は拡張子を見ない）。結果、merge がそれを読んで ValueError: … is not readable JSON を投げ、そのデータセットが読めなくなる。最初に出る症状は、該当データセットの一覧・run 作成・採点が揃って同じ ValueError で落ちること。他のデータセットは無事なので原因が絞りやすい一方、復旧は手でファイルを消すしかない。
リモート側では、write_many の途中で落ちると一部だけが上がる（一括でも原子的ではない）。score_run はそれを見越して row.json を最後に分けているが、rescore の予測コピーには同じ保護が無く、予測が部分的にコピーされた新 run ができる。

DuckDB だけ fsspec を通らない — 認証経路が二本ある

コード確認済み

I/O とネットワーク

選んだ方式storage.py は fsspec のみ（「boto3 を import しない」とモジュール docstring が宣言）。しかし query._connect は DuckDB に httpfs / aws 拡張を読ませ、CREATE SECRET … PROVIDER credential_chain で独自に認証する。aws 拡張が入らない環境では except Exception で環境変数から直接 s3_access_key_id 等を設定するフォールバックに落ちる。duckdb_path が、ローカルはプレーンなパス・リモートは URL を返して両者を橋渡しする。

一般解説

一般解説 — このコードの事実ではありません

この設計が前提にしている S3 の保証（一般解説）

このコードの「ロックが要らない」という主張は、S3 側の2つの性質に寄りかかっています。どちらも cairn のコードには書かれていない外部の事実なので、切り分けて置きます。

1. PUT は単一キーについて原子的。 読者は「書かれる前」か「書かれた後」しか見ず、途中は見ません。だから write_bytes はリモートで一時ファイルを使いません。ただし原子的なのは1キーだけで、複数キーの一括書き込み（fs.pipe）は原子的ではありません — 上のカードで score_run が row.json を分けている理由がこれです。

2. 2020年12月以降、S3 は read-after-write と LIST の両方で強一貫。 それ以前の S3 は LIST が結果整合で、「書いたばかりのキーが LIST に出てこない」ことがありました。もしそれが今も真なら、snapshot が取り逃したファイルを後から拾ってしまい、「スナップショットは不変」という主張が成立しません。GCS も同様に強一貫ですが、MinIO や他の S3 互換ストアが同じ保証を出すかは実装次第です。CAIRN_ROOT を S3 互換ストアに向ける場合、ここが暗黙の前提になります。

逆に、S3 が提供しないもの：compare-and-swap、条件付き書き込み（cairn が使う API の範囲では）、複数キーにまたがるトランザクション。この3つが無いという事実が、この層のほぼ全ての判断の出発点です。
